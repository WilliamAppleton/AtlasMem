# Judge comparison and cascade tuning (3 October 2026)

**Result:** `CascadeJudge(fast=clef, slow=gpt-oss:20b, low=0.3, high=0.95)` made no errors on 81
tuning cases or 92 held-out cases. It escalated 12-18% of cases and averaged 6-7 s per case,
against 16-18 s for `gpt-oss:20b` alone. Those thresholds are now `CascadeJudge`'s defaults.
`clef-flash` is not safe as a judge: it accepted 22 of 39 failures.

## Setup

| | |
|---|---|
| Hardware | One NVIDIA DGX Spark (GB10, 128 GB unified memory) for all local judges |
| Ollama | 0.35.1, `OLLAMA_NUM_PARALLEL=3`; evals run with `--workers 3` |
| `gpt-oss:20b` | Ollama ID `17052f91a42e`, LLM judge with the evidence check |
| `clef` | Ollama ID `2bb11a61d1fb`, 27B, Q4_K_M |
| `clef-flash` | Ollama ID `2aa4d39fd93b`, 9.1B, Q8_0 |
| `jev-latest` | TypeSafe cloud API (`https://api.typesafe.ai`); an alias that moves between releases |

System One judges are scored at P(success) >= 0.5 when run alone. Jev's latency is a round trip
to a cloud API, so it is not directly comparable with the local judges.

## Judges alone

Seed 11, `--tasks 10 --noisy`, 81 cases: 39 failures and 42 successes, including 34 real
trajectories from `scripts/data/real_cases.jsonl`.

```bash
python scripts/eval_judge.py --tasks 10 --noisy --workers 3 \
  --judge llm:gpt-oss:20b@http://<host>:11434 --judge s1:clef-flash@http://<host>:11434 \
  --judge s1:clef@http://<host>:11434 --judge s1:jev-latest@https://api.typesafe.ai
```

| Judge | Accuracy | False accepts | False rejects | Median latency |
|---|---|---|---|---|
| `gpt-oss:20b` | 100% | 0 / 39 | 0 / 42 | 15.3 s |
| `jev-latest` | 95.1% | 4 / 39 | 0 / 42 | 0.23 s (cloud) |
| `clef` | 92.6% | 6 / 39 | 0 / 42 | 4.3 s |
| `clef-flash` | 72.8% | 22 / 39 | 0 / 42 | 1.8 s |

Failures correctly rejected, by type:

| Failure type (cases) | `gpt-oss:20b` | `jev-latest` | `clef` | `clef-flash` |
|---|---|---|---|---|
| `skip_state` (7) | 7 | 3 | 6 | 0 |
| `wrong_target` (10) | 10 | 10 | 10 | 10 |
| `similar_object` (10) | 10 | 10 | 7 | 7 |
| `claimed` (10) | 10 | 10 | 10 | 0 |
| `real_failure` (2) | 2 | 2 | 0 | 0 |

- `clef-flash` accepts nearly any trajectory that looks finished. Its mean P(success) was 0.81
  on `claimed` cases and 0.94 on the real failures.
- `clef` misses look-alike objects and both real failures, one of which is the mug placed for a
  cup. It scores those real failures around 0.9, confidently wrong.
- `jev-latest` misses only skipped state steps, such as a mug that was never cleaned, which it
  scores near 0.5.

## Cascade tuning

`scripts/cascade_sim.py` runs each judge once per case, then simulates every (`low`, `high`)
band from the recorded probabilities, verdicts and latencies. A case escalates to the slow judge
when `low <= P < high`. Thresholds were picked on seed 11, then checked on seed 12: 20 new
tasks with no overlap, 92 synthetic cases, and no real trajectories.

```bash
python scripts/cascade_sim.py --tasks 10 --noisy --slow llm:gpt-oss:20b@http://<host>:11434 \
  --fast s1:clef@http://<host>:11434 --fast s1:jev-latest@https://api.typesafe.ai
python scripts/cascade_sim.py --tasks 20 --seed 12 --noisy --no-real ...   # held-out check
```

| Setup | Seed 11 (tuning, 81 cases) | Seed 12 (held out, 92 cases) |
|---|---|---|
| `gpt-oss:20b` alone | 98.8%, 17.7 s mean | 100%, 15.6 s mean |
| clef cascade, 0.1 / 0.9 (old default) | 98.8%, 17% escalated, 6.8 s | 100%, 30% escalated, 8.4 s |
| **clef cascade, 0.3 / 0.95 (new default)** | **100%, 12% escalated, 6.0 s** | **100%, 18% escalated, 7.0 s** |
| jev cascade, 0.1 / 0.9 | 98.8%, 46% escalated, 9.2 s | 100%, 36% escalated, 5.2 s |
| jev cascade, 0.3 / 0.85 | 100%, 23% escalated, 5.0 s | 100%, 16% escalated, 2.7 s |

Times are mean seconds per case, including escalations. `gpt-oss:20b` false-rejected one real
success in the seed 11 rerun, even at temperature 0. In the cascade, both fast judges accepted
that case confidently, so it never reached the slow judge.

How close each fast judge came to its thresholds:

| Fast judge | Seed | Highest-scoring failure | Lowest-scoring success |
|---|---|---|---|
| `clef` | 11 | 0.907 (`real_failure`) | 0.842 (`real_success`) |
| `clef` | 12 | 0.800 (`similar_object`) | 0.880 (`correct`) |
| `jev-latest` | 11 | 0.800 (`skip_state`) | 0.680 (`real_success`) |
| `jev-latest` | 12 | 0.820 (`skip_state`) | 0.340 (`correct`) |

- **Why `high=0.95`:** the old 0.9 accepted a real failure that clef scored 0.907.
- **Why clef over Jev:** clef keeps wide margins on held-out cases. Jev cleared its picked
  thresholds by only 0.03 on one side and 0.04 on the other. Clef also runs locally, with
  no per-call cost.
- **Possible refinement:** `low=0.4` also made no errors on both seeds and escalates slightly
  less. It has not been adopted.

## Limits

- **A small synthetic world.** Most cases come from the kitchen environment. These results show
  how judges behave on this task, not how they rank as general-purpose judges.
- **Two real failures decide `high`.** The held-out set has no real trajectories, so that
  pattern has not been re-tested. More real failures in `real_cases.jsonl` would firm it up.
- **Thresholds are model-specific.** Re-run `cascade_sim.py` for any other fast model or
  version. `jev-latest` and `clef` will change over time.
- **One machine, one date.** Latencies depend on hardware, quantization and parallel slots.
